# Primary sources reshape DT's rhythm plan

Primary evidence confirms most of round 1's reference-game claims, overturns four of them, and leaves the numeric RPG-budget claims (Hollow Knight notches, Nine Sols jades, Dead Cells banking, Darkest Dungeon's 200-stress outcome) at secondary level. The four reversals are these. Open-source rhythm games do publish their judgement windows. Hi-Fi Rush's GDC page does not support "hits land on the beat". Darkest Dungeon's designers chose to show stress as a number, which undercuts it as precedent for hiding state. Sea of Stars combo points now persist after battle. The sotn-decomp code also closes five SotN gaps: two-handed weapons are one item id written into both hand slots, the only map percentage is `rooms * 100 / 942` on the save title, familiar behaviour changes in ten bands keyed to `level / 10`, the Sword familiar item is granted once at level 50, and motion inputs are matched by an exact-match state machine with a 20-tick window per step. For rhythm tracking, Godot 4.7.1 on Windows sets a hard floor. `InputEvent` carries no timestamp, every key reaches script once per frame at frame start, audio is mixed in 512-frame chunks, WASAPI runs in shared mode only, `get_output_latency()` is a snapshot taken when the device opens, and scheduled playback exists only as an unmerged pull request. The candidate random error is about ±10 ms at 60 Hz, so a Perfect window narrower than about ±20 to 25 ms would punish the engine, not the player. Every number below is a candidate to measure in Phase 5, and nothing was run because no Godot binary is available here. The report ends with a consolidated question list (grouped by DT system) and an open-gaps table. The pair-bond integer, Ciphera rig assist and growth-credit log (approved by the author on 2026-11-05) are treated as in Tier 1, and everything else is an option, not canon.

Three patterns run through the ledger. First, code beats prose: every upgrade that settled a number (windows, familiar bands, the 942 denominator, the level-50 grant) came from source, while every claim that depended on a wiki or guide for a number stayed secondary. Second, developer-stated *intent* is the one thing patch notes and interviews do deliver, and it argues for legibility (Darkest Dungeon's visible meter, Hi-Fi Rush's optional rhythm, Kennedy's and Sasko's visibility rules, Patapon 3's music chosen so "it was clear when you were pushing the buttons correctly"). Third, the dread-versus-brutality and beat-versus-backwards corrections show that second-hand developer facts drift: round 1's own paraphrases were the source of both errors. The reference numbers DT might borrow for budgets and bonds (notch counts, rank thresholds, stress odds) are not borrowable from primary evidence at all, so DT's values have to come from its own playtest data.

## Rhythm pipeline: Godot 4.7.1 leaves about ±10 ms of random error before the player acts

The pipeline is audio clock, song position, beat map, input timestamp, judgement, feedback, with a separate visual path. Every engine claim in this section is [P1] reading of the `4.7.1-stable` source, and every figure marked "candidate" is arithmetic from that reading, not a measurement.

| # | Stage | Godot 4.7.1 mechanism [P1] | Error type | Candidate budget (95th percentile, untested) | Mitigation |
|---|---|---|---|---|---|
| 1 | Audio clock | `get_playback_position()` advances in mixed chunks; `get_time_since_last_mix()` is a wall-clock stamp taken when the audio thread starts a 512-frame chunk ([audio_server.cpp](https://raw.githubusercontent.com/godotengine/godot/4.7.1-stable/servers/audio/audio_server.cpp)) | Random: 10.7 ms chunk at 48 kHz, non-atomic reads | ±3 ms after filtering (raw ±10.7) | Hybrid anchored clock with monotonic filter |
| 2 | Position to heard time | `get_output_latency()` is `real_latency` set once at device open; WASAPI is shared mode only ([audio_driver_wasapi.cpp](https://raw.githubusercontent.com/godotengine/godot/4.7.1-stable/drivers/wasapi/audio_driver_wasapi.cpp)) | Constant per device, plus unmodelled Bluetooth, USB or driver delay | Residual ≤ ±8 ms after calibration | Per-device offset; re-prompt on device change |

| 7 | Visual feedback | Next frame plus one to three swapchain frames | Constant plus ±1 frame | Calibrated visual offset | Separate visual offset; no interpolation on judged nodes |

### Clock and input: judge on audio-side time, stamp in `_input`

Three engine facts shape the first four rows. The Windows loop calls `process_events()` and then `Main::iteration()`, which runs `_physics_process` before `_process`, so a key pressed mid-frame waits in the Win32 queue until the next frame start ([os_windows.cpp](https://raw.githubusercontent.com/godotengine/godot/4.7.1-stable/platform/windows/os_windows.cpp), [main.cpp](https://raw.githubusercontent.com/godotengine/godot/4.7.1-stable/main/main.cpp)). `use_accumulated_input` is irrelevant because only mouse-motion and screen-drag events implement `accumulate`, and agile event flushing is documented as Android-only ([ProjectSettings.xml](https://raw.githubusercontent.com/godotengine/godot/4.7.1-stable/doc/classes/ProjectSettings.xml)). The only usable timestamp is `Time.get_ticks_usec()`, which is monotonic and `QueryPerformanceCounter`-based, read at the top of `_input`. The consequence is that frame hitches matter more than any input setting: a 60 ms hitch adds up to 60 ms of judgement error. Polling in `_physics_process` adds a second quantisation and is ruled out. A native GDExtension reading raw input with its own timestamps would remove the frame quantisation, but it needs a native build and sits at T2 or later, only if Phase 5 shows input jitter dominates.

The clock recommendation is a hybrid. Godot's own guidance offers a system-clock method and a hardware method, and warns that adding `get_time_since_last_mix()` and subtracting latency "may be a bit jittery". The hybrid takes a system-clock anchor, `(ticks_usec_at_play, expected song position)`, which can be queried at any instant (essential because `_input` and `_process` run at different instants), and corrects it slowly toward the hardware estimate `position + time_since_last_mix - output_latency`, with a hard resync above a candidate 30 ms. Funkin's equivalent is a conductor eased toward audio time with `1 - exp(-42 * dt)` and a hard resync above 65 ms, and its source comment says raw audio position "had low-precision steps that made note scrolling stutter" ([PlayState.hx](https://github.com/FunkinCrew/Funkin/blob/main/source/funkin/play/PlayState.hx)). Funkin has no handling for a backwards-moving clock, so "song time never decreases between frames" is a DT addition. `AudioStreamInteractive` returns a playback position of 0.0, so adaptive music needs the anchor re-set at every clip transition. Because `get_output_latency()` is a snapshot ([issue #38215](https://github.com/godotengine/godot/issues/38215) reports it as inaccurate and it is still open), DT should poll `AudioServer.output_device` and the latency every few seconds and prompt recalibration when either changes. Judgement then reads `judged_delta = (input_ticks_usec - anchor_usec) / 1e6 + anchor_song - beat_time - input_offset`.

The root-sum-square of rows 1, 4 and 6 is about 10.3 ms at 60 Hz and 6.7 ms at 144 Hz (my arithmetic on candidate inputs). That sets a floor on window design. ITGmania's W1 is 22.5 ms, osu!mania's Perfect is 22.4 ms at OD0 and 13.9 ms at OD10, and Quaver's Marvelous is 18 ms. Windows of that size assume sub-millisecond timestamps, which GDScript on 4.7.1 cannot supply. DT's top tier should sit well above them.

### Three sequence grammars, and where each touches the combo lock

The grammars below are options, not decisions, and none has been prototyped. All three can give Vox and Ciphera different effects on the same token grid, so "instrument as verb" costs nothing extra in the recogniser.

**Grammar A, per-beat grid** (NecroDancer lineage, [P1]). One graded action per active member per beat, judged against the nearest beat. Actors act on divisors of the beat (candidate: Basic Bot every 2, Flying Drone every beat or on a pattern, Heavy Unit every 4 with a visible wind-up, from an [S] paraphrase), and the player's action wins ties. Rests are beats with no input. It is the cheapest build and the easiest to calibrate. The cost is that stress drifts timing, which Clark observed. It does not touch the combo lock.

**Grammar B, call-and-response phrases** (Patapon lineage, [P2], thin on internals). A device or enemy states a one-measure phrase of explicit tokens (press, rest, hold) and the player repeats it. Recognition is an incremental cursor that fails at the first wrong token, which is my choice and unverified against Patapon. Rhythm Doctor's explicit marks for held beats and silent beats show the representation works ([Game Developer](https://www.gamedeveloper.com/design/using-medical-stories-and-heart-conditions-to-create-musical-challenges-in-rhythm-doctor)). It fits the environmental puzzle and the micro-choice, but it **can touch the combo lock**: a fixed phrase is a "combination of presses", and the author has excluded combo systems from T1. Kotani's worry about memorising complex commands and the "don, dodon, dodon" difficulty argue for very short phrases.

**Grammar C, free attack snapped to the beat** (Hi-Fi Rush lineage, [P2]). The player presses freely, the impact is quantised to the beat, and the grade scales damage and hit-stop length rather than whether the hit lands. It is the most forgiving and matches Johanas's "even if you aren't perfect" line. The snapping mechanism is unconfirmed (stretching versus alternate clips), and combos are its natural extension, so it **can touch the combo lock** the moment two attacks chain. Keeping it to single actions stays inside T1.

Whichever grammar is chosen, SotN's matcher is the reference for how a sequence is recognised: one record per sequence holding a step counter and a countdown, an exact-match test per step, a reset on timeout, a completion latch that combat consumes, and facing captured at the start. DT would replace "20 ticks" with a beat window around each step's target beat, and let a wrong press reset only that sequence, not the encounter. Chord slots (two presses on one beat) have no single precedent: ITGmania judges rows as a unit, osu!mania and Funkin judge each lane independently, so "worst, first or last press" is a DT decision. Any multi-step matcher, including chords, also needs the same lock check as Grammar B.

### Calibration and feedback scheduling

The calibration options from the code and developer sources are compatible and can be layered. ITGmania's auto-sync takes 24 offset samples and applies the mean only if the standard deviation is under 30 ms ([AdjustSync.cpp](https://github.com/itgmania/itgmania/blob/release/src/AdjustSync.cpp)), and its default global offset is -8 ms ([PrefsManager.cpp](https://github.com/itgmania/itgmania/blob/release/src/PrefsManager.cpp)). Rhythm Quest's developer describes a two-phase test, audio-visual sync and then an input tap test, about ten taps with the minimum and maximum discarded, and warns that "we can never measure a single type of latency by itself" ([devlog 10](https://rhythmquestgame.com/devlog/10.html)); the Rhythm Doctor detail there is second-hand. osu!'s post-play suggestion needs at least 50 timed hits and computes `currentOffset - median * exp(-0.0116 * (UR - 90))` when unstable rate is 90 or more, else the plain median ([BeatmapOffsetControl.cs](https://github.com/ppy/osu/blob/master/osu.Game/Screens/Play/PlayerSettings/BeatmapOffsetControl.cs)). NecroDancer's leaky integrator adapts continuously. Funkin keeps `globalOffset` (input) and `audioVisualOffset` as separate settings ([Conductor.hx](https://github.com/FunkinCrew/Funkin/blob/main/source/funkin/Conductor.hx)). For DT the candidate stack is a first-launch two-phase tap test with the ITG 24-tap and 30 ms gate, per-device persistence keyed on `AudioServer.output_device`, a manual slider, and an optional osu!-style suggestion fed by the growth-credit log. One trap is specific to DT: a silent continuous auto-calibrator would shift which hits earn Perfect and Good credits, so the log should store the raw signed offset and the offset applied at the time, and any adaptive correction should be capped and visible. An optional beat meter (Hi-Fi Rush [P2], from a search summary of the Q&A) matters more than usual because DT signals choices by tone alone.

Feedback has no native scheduling. Neither `AudioStreamPlayer` nor `AudioStreamPlaybackPolyphonic.play_stream` takes a start time, and `play()` begins only when the audio thread processes the next chunk. Scheduled playback was proposed in PR #105510 (closed unmerged 2025-06-06) and continues as open PR [#107226](https://github.com/godotengine/godot/pull/107226) (`play_scheduled`, `get_absolute_time()`), whose stated problems include absolute time jumping on device change and silence mixed for every queued sound. It is not in 4.7.1, so T1 must not depend on it. The candidate response has three parts. Player-triggered hit sounds are reactive and cannot be pre-scheduled anyway: use short pre-loaded streams in a pool or `AudioStreamPolyphonic`, with expected latency about 15 to 26 ms at the 15 ms default (my estimate: 0 to 10.7 ms to the next mix plus output latency). Enemy telegraph and metronome cues are fired at `target_song_time - (output_latency + mean time_to_next_mix)`, evaluated every frame, for jitter no worse than a frame plus 10.7 ms. Tight cues can be baked into a cue stem started in the same frame as the music, which should be sample-locked (inference). Miss feedback goes on its own bus so a miss never silences music layers. Visuals are drawn at `song_time + visual_offset`, and judged elements stay out of interpolated physics branches, because Godot's own jitter page says physics interpolation increases input lag and singles out "fixed-framerate genres like fighting and rhythm games" ([docs](https://docs.godotengine.org/en/4.7/tutorials/rendering/jitter_stutter.html)). Candidate engine settings for encounters (all untested): V-Sync on, `physics_ticks_per_second` of 120 if CPU allows, swapchain image count 3 first and 2 as a test, and a frame cap of `r - r*r/3600` only on variable-refresh displays. Judged animation contact frames read `song_time`, not physics ticks.

### Phase 5: six scenes, run on the real PC

The plan targets the RX 5700 XT machine and every output device DT might meet. Each scene writes CSV from one shared rhythm log with these fields: frame, input ticks, frame-start ticks, hardware and anchor song time, anchor correction, beat time, signed delta in ms, tier, output latency, time since last mix, output device, refresh rate, physics ticks per second and frame time. The growth-credit log and the pair-bond integer read tiers from that same record and do not re-time anything. The author's Godot path is needed to run any of it.

| Scene | What it does | Candidate pass line (all untested) |
|---|---|---|
| S1 ClockProbe | Play a 5-minute stem; log position, time since and to next mix, output latency; compare both documented methods and the hybrid; vary V-Sync, 60 and 144 Hz, windowed and fullscreen; capture the driver's `--verbose` WASAPI lines | Zero backward steps; jitter ≤ 3 ms; 5-minute drift ≤ 5 ms; no steady-state hard resyncs |
| S2 InputStampProbe | Human taps to a metronome; compare `_input`, `_physics_process` polling and accumulated input on or off, ideally against a camera or contact-mic reference | Run-to-run mean stable to ±3 ms; std dev ≤ about 5.8 ms at 60 Hz |
| S3 LoopbackKeySound | Key press to hit sound via one player, a pool of 8 and `AudioStreamPolyphonic`; record physical key click and speaker on two channels; 100 presses each | Median key-to-speaker ≤ 40 ms wired or speakers, std dev ≤ 5 ms; Bluetooth reported, not gated |
| S4 FrameStress | S1 plus random 30, 60 and 100 ms hitches | Judgement error tracks hitch length; anchor recovers; p99 frame time ≤ 1.25 refresh intervals in encounters |
| S5 DeviceSwap | Hot-swap speakers, wired and Bluetooth mid-run; log device and latency before and after | Recalibration prompt fires on every swap |
| S6 CalibrationScreen | Two-phase tap test, 10 taps each, min and max trimmed, three repeats per device | Repeat spread ≤ 8 ms; residual p95 ≤ 10 ms; overall system error p95 ≤ 12 ms at 60 Hz and ≤ 8 ms at 144 Hz |

If S3 exceeds about 50 ms, lowering `audio/driver/output_latency` is the first lever, at a CPU and crackle cost, but the 512-frame mix floor stays. If S2 shows input jitter dominating the budget, the raw-input GDExtension becomes a T2 candidate.

## Conclusion

The round 2 evidence changes what DT should trust. Numbers that matter for the rhythm evaluator are knowable from open code and the engine source, so DT can set windows from the measured noise floor instead of from folklore, and the Godot findings show the genre's tightest tiers are out of reach in GDScript on 4.7.1. By contrast, the budget-and-bond numbers that round 1 treated as borrowable (notches, stress odds, rank thresholds) have no primary source, which argues for building DT's own values from the hit log it is already approved to keep. The approved log is therefore the most leveraged item in Tier 1: it feeds calibration suggestions, growth credits, the pair-bond integer and playtest tuning, so its schema (signed offsets from the first build) is worth settling before any grammar.

The second implication concerns legibility. Darkest Dungeon's designers reversed toward showing state, Hi-Fi Rush treats rhythm skill as optional, and Failbetter, Kennedy and Sasko all say unnoticed consequences are wasted. The hidden pair-bond integer is approved, but the primary evidence says a hidden value works only when its effects are readable through tells, and that is a decision the author owns.
